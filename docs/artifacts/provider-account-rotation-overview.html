Provider accounts · Selection & recovery

Keep the work.
Change the account.

When a subscription reaches its limit, the session should have a way forward. Switch its account without starting the work over, and spread new sessions across your subscriptions.

Manual switching + random selection first.
Automatic fallback and round robin are optional follow-ups.

Choose once. Keep it pinned.

Selection decides which account a new session starts with. It is not per-request routing, and it does not change accounts in sessions that already exist.

Random is the recommended first release. Repeats are normal; it spreads assignments, not measured tokens or cost.

Illustrative assignments, not live quota data. Eligible means active, compatible, and included in the selected pool—not guaranteed remaining quota.

What wins over random?
  1. An explicit choiceA named account or API key stays an explicit choice.
  2. A child session's inheritanceCopy the parent's captured account; do not reroll.
  3. Unattended API-key policyPreserve the existing setting for unpinned bots and automations.
  4. Installation selection policyFixed or random applies to remaining compatible provider slots.

No configured policy? Keep today's legacy behavior. A configured pool with no eligible members produces an error—not a silent move to API billing.

Important edge cases: a warmed session keeps its original draw; each automation fan-out session gets its own allocation; reconnecting or refreshing a token never rerolls the account.

“Selected” is not “applied.”

A database write cannot replace cached credentials. Dispatch stays paused until the correct runtime acknowledges the exact binding revision and the old execution is stopped.

Continue is a new intent.

The original failed turn remains in history. The user resumes queued work or submits a new continuation. The platform never silently replays the old prompt or its tool effects.

01

Bound the restart grace.

Declare an intentional disconnect before restarting. Only that operation gets grace, and retries cannot extend its absolute deadline.

02

Timeout stops retries.

A deadline produces a visible reconciliation state. It is not permission for the next generic alarm to destroy the sandbox.

03

Preserve before stopping.

Paused retention requires verified persistent suspension or a successful current checkpoint. A skipped or failed snapshot is not proof.

A lost acknowledgement means “state unknown,” not “roll back.” Reconcile the same operation and revision. Provider hard lifetimes still apply: surface retention limits and workspace loss honestly; do not promise indefinite compute.

Acceptance checklist — what must be true before release
  • The same workspace and exact conversation survive A → B; the next request really uses B's credentials and account metadata.
  • Old execution and relevant tool descendants have stopped before any new prompt starts.
  • A stale refresh, duplicate command, lost ACK, or replaced sandbox cannot reinstall the wrong account or release dispatch.
  • Heartbeat/inactivity alarms during apply respect ownership; a switch-only boot timeout leaves unrelated queued prompts pending.
  • Grace and operation deadlines survive eviction and never slide on retries; failed preservation cannot trigger destructive fallback.
  • Explicit pins and unattended policy remain intact; warming, first prompt, and reconnect never reroll a durable allocation.
  • Budget exhaustion remains enforced. No silent API-key fallback, terminal-message replay, or blank-conversation recovery.
The goal: a recoverable session, not a disposable one.
