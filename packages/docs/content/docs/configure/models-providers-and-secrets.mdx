OpenInspect connects two different provider layers:

- a **model provider** supplies the language model used by the coding agent;
- a **sandbox provider** supplies the isolated computer where the agent works.

Changing one does not automatically configure the other.

## Choose an enabled model

Administrators decide which models are enabled under **Settings → Models**. Users then choose from
that allowed set when starting interactive work. Integration and automation defaults can select a
model separately.

The exact catalog changes over time. Use the product's model settings as the runtime source of truth
and the repository's
[available-models reference](https://github.com/ColeMurray/background-agents/blob/main/docs/AVAILABLE_MODELS.md)
for model identifiers and reasoning support.

## Provider accounts and API-key mode

OpenAI and xAI can use installation-wide provider accounts. A session can be pinned to an explicit
account, resolve a configured default for future unattended work, or use API-key mode when the
deployment permits it.

A default-account change affects future sessions; it does not silently move existing sessions to a
different account. If an account becomes unavailable, reconnect it or select another allowed mode
before retrying work.

Other model providers can require global API keys. The required key and injection behavior can also
depend on the sandbox provider, so follow the provider-specific guide instead of assuming all
combinations work identically.

## Choose the narrowest secret scope

| Scope       | Applies to                                      | Typical use                                                 |
| ----------- | ----------------------------------------------- | ----------------------------------------------------------- |
| Global      | Every session unless a target overrides the key | Model API key required across the deployment                |
| Repository  | Sessions targeting that repository              | Repository-specific service or test credential              |
| Environment | Sessions launched from that saved environment   | Shared credential for a reusable multi-repository workspace |

Repository secrets override global values with the same key. For ad-hoc multi-repository sessions,
the primary repository wins collisions. Environment sessions use environment secrets instead of
their repositories' secret sets.

## Handle secrets safely

- Add secrets through the settings interface; never commit them.
- Use recognizable key names and document their purpose without recording values.
- Remember that clients can see key names even though they cannot retrieve values.
- Do not paste credentials into a prompt or support report.
- Rotate a credential when its exposure is suspected; deleting a configured value is not proof that
  every external provider copy, backup, or existing sandbox has been purged.
- Start a new session when you need it to consume changed target configuration.

For the complete operational procedure, see
[Secrets Management](https://github.com/ColeMurray/background-agents/blob/main/docs/SECRETS.md),
[Using OpenAI Models](https://github.com/ColeMurray/background-agents/blob/main/docs/OPENAI_MODELS.md),
and [Using Grok](https://github.com/ColeMurray/background-agents/blob/main/docs/GROK_MODELS.md).
