# OI-CONFORMANCE.md — the §7 self-audit

**Yardstick:** `OPEN-INSPECT-REFERENCE-MODEL.md` §7 (rows A1–I-4, the 14 suspects, the self-check
protocol). **Branch audited:** `compound/pi-overlay` — the core (`oi-core-end`) plus the overlay,
with `feat/pi-go-live-integration-v2` @ `be4fc772` kept as the reference the equivalence diff is
measured against.

**How to read this.** For every row: the Pi code path with `file:line`; **PASS / FAIL / N/A**; the
three-question test — (1) does the Pi path go through the named upstream code (R) or a
harness-neutral replacement (N/X)? (2) is the decision taken from **current** authority **at time of
use**, by the session, not by Pi? (3) is there a test that **fails if the check is deleted**? — and
the name of that test.

> **A row is not PASS without that test.** Any **N** or **X** row whose code lives under a
> Pi-specific package or is named `pi*` is a **FAIL by definition**. Any **I** row with a reachable
> path is a **FAIL** regardless of tests.

## What is in the overlay

Three capabilities Open-Inspect does not have today, all off by default, all documented in
`DEVIATIONS.md`: the **personal MCP lane** (one person's own OAuth credential, re-evaluated against
current authority at every call), the **external-action approval ledger** (an effect that changes
something outside the model is prepared, and a human decides), and **cross-session messaging** (a
session hands a message to another session, with the fan-out bounded and the provenance recorded).

The overlay's migrations take the `9xxx` block: `9001` the external-action ledger, `9002` the
personal MCP credential storage, `9003` the cross-session receipts, `9004` the session grants.

## The projection defect, and what it was

The turn's events did not reach the session's events, and the reason was three defects, not a wrong
test:

1. **A control's turn was named by the control's request id**, while the session recorded it as the
   message `pi-control:<requestId>`. Every capability call that named the operation — the
   credential, the projection, the events — was refused, so the turn never ran. The control now
   names the session's operation
   (`packages/control-plane/src/session/http/handlers/pi-control.handler.ts`), and the Durable
   Object writes that id into the turn's request id.
2. **The fence knew only the control's request id** (`pi-operation-fence.ts`), so a control's turn
   was not a live turn of the session; it now recognises the message id a control starts
   (`pi-control-message-id.ts`).
3. **A control that named no model ran on the harness's default model** rather than the session's,
   so the turn asked a provider the session was not connected to.

With those fixed, the session's own `events` table receives the turn's `step_start`, `step_finish`
and `execution_complete` — `/internal/pi-event` answers 200 for every projection — and the export
carries them.

## What is still open, and who owns it

1. **The overlay's migration numbers are frozen** (the `9xxx` block). A renumber after an
   application is a **deployment that stops**, not a skip. The CI guard now fails the build if
   upstream takes the block; the guard script is in the repository, and the workflow that calls it
   still has to be added.
2. **The tool call is still open.** The events reach the session and the export carries them, but
   the model's tool call does not: the turn's model call ends with the error
   `No tool named "bash" is currently available`, which comes from the computer-workspace
   extension's tool surface (`@cloudflare/computer`), and the faux provider the integration tests
   install is not the one the turn asks. Until that is root-caused, **G-5's tool-call half is FAIL,
   not PASS**, and its delete-the-check proof does not exist yet. The projection half — that every
   step of a turn reaches the session's own events — is proven.
3. **The decisions that are the user's**: the D8 authority split, delete semantics, revocation
   inside a replaying Code Mode script, which models Pi may serve, personal MCP in unattended
   sessions, the E-2 question of whether an unattended Pi session may run on a person's
   subscription, and whether the model-visible shell (D-1) is acceptable given that the execution
   sandbox re-contains it.

## The headline

The branch is **not** a Pi-shaped fork of Open-Inspect. It is a genuine harness-neutral seam with Pi
as its first harness, and most of the architecture is right: the Pi Durable Object mints **no**
principal at all, every capability call goes back through the SessionDO, the tool surface is
default-deny, and the Code Mode sandbox is a separately deployed Worker.

**The failures are concentrated in three places**, and all three are _naming and placement_, not
mechanism:

1. **B-8 (I row) — the runtime `env` is the whole control-plane env.** The containment that the
   sandbox gave for free is, for the env, still held by **compile-time discipline** rather than
   structure. This is suspect #1, and it is **real**.
2. **The N rows' replacements live under `packages/control-plane/src/pi/` and `pi*` names.** By §7's
   own rule, that is a FAIL by definition. The _mechanism_ is right; the _home_ is wrong.
3. **Two capabilities that Open-Inspect does not have today** — the external-action approval ledger
   and personal MCP with OAuth — are mixed into the same branch as the core seam, so the branch can
   merge neither upstream nor cleanly into our deployment.

## The findings, ranked

Every row in §7 has a verdict above. This is the order they should be fixed in: the **I rows and the
real bugs** first, then the **W → X rows that are not built**, then the **placement failures**, then
the **missing proof**.

### 1. **B-6 / B-5 — the author-authority re-check is absent.** (I-row severity, W → X)

The Pi path's only gate is an _activity_ check —
`packages/control-plane/src/session/http/handlers/pi-operation-fence.ts:15-19` says so in its own
docstring: _"The fence is an activity check, not an identity check."_ A user suspended, or removed
from the team, **after** a turn started keeps that turn's capabilities until the turn ends —
credential, repository tools, browser, code mode, memory, MCP, external actions. The upstream
template that performs exactly this read
(`packages/control-plane/src/routes/session-children.ts:64-93` → `getEffectiveAuthorization` +
`TeamMembershipStore`) is not used anywhere in the Pi tree, and only _one_ tool — cross-session —
does it at all. **Fix, in core, harness-neutral:** a "the turn's author is still authorized" check
before each model call and each tool action, with a test that fails without it. _One fix closes B-5
and B-6 together._

### 2. **B-8 — the runtime `env` was the whole control-plane env.** (I row) — **FIXED**

`index.ts:26` exports the Pi DO from the control-plane Worker; `pi-durable-object.ts:195` narrowed
the _type_ only, so at runtime the object held every secret. **Fixed on this branch**: the env is
scoped _before_ it reaches the base class
(`packages/control-plane/src/cloudflare/binding-scope.ts`), so the object physically holds no
secret. The test is `packages/control-plane/test/integration/pi-session-do.test.ts` — "holds no
deployment secret in its runtime bindings". The helper is harness-neutral, so it goes to core as-is.

### 3. **Suspect #5 — the stale pin.** (HIGH severity, real bug, still open)

The personal MCP lane never re-evaluated the server's `repo_scope`, its `enabled`, or the catalogue
hash at invocation time. A narrowed scope, a disabled server, and a withdrawn tool all stayed
callable — the _shared_ lane got this right (`db/mcp-servers.ts:347-361`), the personal lane did
not. And **no test exercised `broker.callTool` at all**. This is the ledger's §1d "real bug, highest
priority code fix".

**Fixed on this branch.** One harness-neutral decision function now answers the question, and it
answers it at _every_ path that touches a grant:

- `packages/control-plane/src/session/mcp-grant-scope.ts` — `evaluateMcpGrantScope` (the server
  exists, is enabled, and its repository scope still covers a repository the session holds) and
  `evaluateMcpGrantTool` (the tool is in the **frozen** pin set _and_ in the server's **current**
  reviewed set — so widening the review never adds a tool to an old grant, and narrowing it does
  remove one).
- Wired into the **grant** path (`components.ts`), the **roster** path (a grant that is no longer in
  scope is not listed, so it is not offered as a capability it does not have), and the **call** path
  (the scope is re-read before the broker is touched).
- `packages/control-plane/test/integration/mcp-grant-scope.test.ts` — five cases against real D1:
  allowed, scope narrowed, server disabled, review moved on, and a tool the pin never froze.
  **Demonstrated:** deleting the scope check makes the narrowing case fail; restoring it makes it
  green again.

**Still open:** the _call site_ in `components.ts` is not itself covered by a test — the integration
test proves the decision, and the wiring is what Phase 4 proves by deletion.

### 4. **H-3 — the budget cap is never checked before a model call.** (N row)

Grep for `budget`, `max_cost`, `maxCost` across `packages/control-plane/src/pi/` and the Pi DO
returns **zero hits**, and the capability snapshot the DO holds carries no budget field. The cap is
enforced only _after_ a priced step crosses it, and the abort is asynchronous. That is exactly the
upstream weakness the row exists to replace. **Fix, in core:** a harness-neutral budget port the DO
consults before every model call, with a test that fails when the check is removed.

### 5. **D-3 — no per-turn deadline owned by the DO.** (N row)

Cancellation exists and is tested; the _deadline_ does not. Nothing bounds a single provider call
inside the DO, and `EXECUTION_DEADLINE_GRACE_MS` is never applied on the Pi path (it exists only on
the sandbox prompt deadline). **Fix, in core:** a harness-neutral turn-deadline and cancellation
port.

### 6. **G-2 — session-DO migration id 57 was unreserved.** (real latent bug) — **FIXED**

`session/schema.ts` used a bare literal `57` with no `feature:` marker, and 57 was absent from the
reservation registry. Because the runner skips by **id**, upstream's next session-DO migration would
have been **silently skipped** wherever Pi's 57 had already run. **Fixed:** 57 is reserved, D1
version 90 is reserved too, and both migrations declare the feature that owns them.

### 7. **G-3 — the archive is not durably quiescent.** (real bug)

The Pi DO keeps no archived marker and `onStart` resumes pending work on every activation
(`pi-durable-object.ts:757`), so an archived session can wake up, resume the agent, and keep
projecting into its timeline; the event processor has no archived guard. **Fix:** an archived marker
that refuses to resume or project, plus a test that fails when the marker check is deleted.

### 8. **A2 — an unknown harness id falls back to OpenCode.** (W row)

`harnesses.ts:82-84` keeps upstream's fallback. A Pi session read by a binary that does not know

fallback. The row asks for a **fail closed**. **Fix:** refuse.

### 9. **The N rows' replacements live under `pi` names.** (class rule — the largest single finding)

§7 says an N or X row implemented in a Pi-specific package or under a `pi*` name is a **FAIL by
definition**, "even if correct". That is true of **D-1** (the deny-by-default tool surface), **D-2**
